# Build the interactive orchestration flow


This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This plan must be maintained in accordance with `PLANS.md` at the repository root. This plan builds on all five prior plans, each checked into this repository: `plans/01_dataset.md` (factor and price data), `plans/02_llm_s_agent.md` and `plans/03_llm_f_agent.md` (the two screening agents), `plans/04_candidate_scanner.md` (consensus logic), and `plans/05_optimizer_and_allocation.md` (weights and share allocation). This plan is the last piece: it runs all of the above together and lets a person steer the result interactively.


## Purpose / Big Picture


After this plan is done, a person can run one command and step through the whole pipeline this project builds, end to end, for a date of their choosing: see which stocks LLM-S and LLM-F each flagged, see the consensus candidate list the scanner produced from those two signals, see the resulting portfolio weights and share allocation under whichever of GMV, MV, or MSR they pick, and then — this is the part `README.md` specifically calls for — add or remove tickers from that candidate list by typing a request, and immediately see the weights and allocation recomputed for the edited list. The same command works two ways: pointed at a historical rebalance date within 2020-01-01 to 2024-04-30 (backtest mode, letting a person watch the paper's whole evaluation window play out and compare against the paper's own reported Sharpe ratios), or pointed at today (live mode, producing an actual current portfolio recommendation using live data).

## Surprises & Discoveries


(The CrewAI interactive-mechanism findings called for by Concrete Steps Step 1, and the full-window backtest findings called for once the runner was implemented, are both recorded below.)


- Discovery (2026-09-04): CrewAI's `@human_feedback` does *not* require an LLM or any API key so long as `emit` is omitted, and a repeated multi-turn edit loop really is expressible in it. Verified by running a throwaway four-method `Flow` against the installed `crewai==1.15.12` with piped stdin (`printf 'add NVDA\ndone\n'`): `@start()` produced a candidate list, a `@listen(or_("show", "again"))` method decorated with `@human_feedback(message="Edit candidates (add X / remove Y / done):")` displayed it and blocked for input, and a `@router` on that method returned `"again"` to loop or a differently-named outcome to exit. The transcript shows the loop body executing twice, once per piped line (`[probe] raw feedback='add NVDA' outcome=None` then `[probe] raw feedback='done' outcome=None`), followed by `[probe] finished` and `[probe] result: ok` with exit status 0, all with no `OPENAI_API_KEY` set and no LLM call made. Two mechanical gotchas found the hard way and worth knowing before anyone tries this again: a `@router`'s returned outcome string must not collide with the name of the handler that listens for it (`return "finish"` feeding `@listen("finish")` on a method named `finish` is rejected at class-construction time by a pydantic validator — `"A listener triggered by its own completion creates an infinite loop"`), and the feedback result is read off the flow instance as `self.last_human_feedback`, *not* `self.human_feedback` as both the live docs and the installed module's own docstring show (`AttributeError: 'ProbeFlow' object has no attribute 'human_feedback'. Did you mean: 'last_human_feedback'?`) — a real docs-versus-code drift in 1.15.12, and exactly the kind of thing `CREWAI.md`'s freshness-check requirement exists to catch.
- Discovery (2026-09-04): CrewAI's synchronous human-feedback path is not a richer input mechanism than a plain prompt — it *is* a plain prompt. `crewai/flow/async_feedback/providers.py`'s `ConsoleProvider.request_feedback` (the default provider when none is passed) collects the answer with a literal `feedback = input("Your feedback: ").strip()`, and `crewai/flow/runtime/__init__.py` has the same `input("Your feedback: ").strip()` call inline on its own path. Structured routing is the only thing the decorator adds on top, and that is gated behind `emit`, which `_validate_human_feedback_options` refuses without an LLM (`"llm is required when emit is specified"`); `HumanFeedbackConfig.llm` defaults to `"gpt-5.4-mini"`, an OpenAI model, whereas this project configures only `settings.llm_s_model = "anthropic/claude-sonnet-4-5"` and an `anthropic_api_key`. So the two available shapes are a bare `input()` with the feedback text handed back unparsed, or a bare `input()` plus a paid LLM round-trip to decide whether the user typed something meaning "add" or something meaning "done".
- Discovery (2026-09-04): the same probe run emitted 162 lines of terminal output for four flow methods and two feedback turns, almost all of it Rich-bordered `Flow Method Running` / `Flow Method Completed` / `Flow Completion` panels emitted by CrewAI's own event listener, with the four lines this plan's CLI would actually care about buried inside them. That is a real cost for a CLI whose stated purpose in Purpose / Big Picture is to *display* legibly why each ticker is or is not a candidate, alongside weights and a share allocation — suppressible, but only by additional work against CrewAI's event bus that a plain prompt loop never incurs.
- Discovery (2026-09-04): `settings.llm_s_model`'s default, `"anthropic/claude-sonnet-4-5"`, does not resolve against this environment's configured `ANTHROPIC_BASE_URL` (an Azure AI Foundry endpoint, `https://idofoundryrg.services.ai.azure.com/anthropic/`) — `run_pipeline`'s first real end-to-end run failed with `anthropic.NotFoundError: Error code: 404 - {'error': {'code': 'DeploymentNotFound', 'message': 'The API deployment claude-sonnet-4-5 does not exist. ...'}}`, the same Azure Foundry deployment-name model that `crewai.LLM` passes straight through to the Anthropic SDK. `plans/02_llm_s_agent.md`'s own manual-run item (2026-08-06) had already worked around this by overriding `LLM_S_MODEL=anthropic/claude-opus-4-8` for that one call, without ever updating `settings.py`'s default — this plan's own manual run hit the identical gap fresh, confirming it is a standing environment/settings mismatch rather than something plan 06 introduced. Re-ran with `LLM_S_MODEL=anthropic/claude-opus-4-8 uv run python -m src.flow.cli --date 2024-03-01 --objective MSR --value 100000` and it succeeded completely (real `generate_rule` LLM call, real `screen`, real `scan_with_detail`, real `compute_weights`/`allocate_shares`) — see Artifacts and Notes for the real output. Not fixed here (out of scope for this Progress item, which is about `run_pipeline`/`cli.py` existing and working, not about `settings.py`'s default model string) but flagged because every future real run of this CLI against the default model will hit the same 404 until either `settings.llm_s_model`'s default is corrected for this Azure Foundry deployment or `LLM_S_MODEL` is set in `.env`.
- Discovery (2026-09-04): DuckDB's `ATTACH` statement (used by `src/flow/live.py`'s `_copy_news_archive` to copy the static `news_articles_hf` table into a live snapshot) does not accept a bound parameter for its target path — `con.execute("ATTACH ? AS src (READ_ONLY)", [source_db_path])` fails with `Parser Error: syntax error at or near "?"`, verified live against the installed `duckdb` version. Every other DuckDB call in this codebase passes its path to `duckdb.connect(db_path)` itself (never inside SQL text), so this is the first place a `db_path` needed to be embedded into a SQL string; resolved by quoting and escaping single quotes (`source_db_path.replace("'", "''")`) and interpolating into the `ATTACH` statement directly, since `source_db_path` is an internal, caller-controlled filesystem path, not untrusted external input.
- Discovery (2026-09-04): building live mode's causally-masked December-of-`as_of.year - 1` membership/factors snapshot turned out to be load-bearing, not optional, for `selection="llm_s_only"`/`"llm_s_and_f"` — initially assumed a single `as_of`-dated snapshot might suffice (there is no look-ahead-bias concern in live mode the way there is in backtest mode, since "today" has no future to peek at), but `generate_rule`'s `resolve_as_of_date` unconditionally queries `factors` for a row strictly before `date(rebalance_date.year, 1, 1)` regardless of which mode called it, and a single `as_of`-only snapshot has no such row — `resolve_as_of_date` would silently fall back to its own earliest-available-date logic and log a "NOT truly causally masked" warning for every live run, defeating the point of reusing `generate_rule` unmodified. Building two membership/factors dates into the same live snapshot (verified for real: `2025-12-01` and `2026-09-04` both appeared with real per-date SEC EDGAR/yfinance-derived factors, and `generate_rule` resolved to the December date without any fallback warning) fixes this with no changes needed to `src/agents/llm_s.py` itself.
- Discovery (2026-09-04): a full real live-mode run at the default ~500-real-ticker scale (`selection="llm_f_only"`, LLM-F's own Anthropic call mocked to avoid ~500 real API calls, everything else real) took 199.6 seconds end to end - roughly 3s for the real Wikipedia membership fetch, ~35s for real yfinance price history across 6 batches (503 tickers x 65 months, 676,239 rows, 0 unresolved), under 1s for `build_returns`, and the remaining ~160s in `screen_month`'s real per-ticker `fetch_headlines` yfinance-news calls (503 tickers at roughly 15s/50 tickers). `selection="llm_s_only"`'s per-ticker cost is structurally different and NOT measured at this same 500-ticker scale in this pass (deliberately deferred to the "manually run... live mode" item, since `build_factors`'s real SEC EDGAR + yfinance balance-sheet/shares fetch is sequential per ticker with its own pause-second throttling, unlike `build_price_history`'s batched, threaded `yf.download` — a small 3-ticker check completed in 13.9s total including two full dates' worth of real factors, which does not extrapolate linearly to 500 tickers x 2 dates given the sequential-fetch design plan 1's own `fetch_all_ticker_fundamentals` already documents).
- Discovery (2026-09-04): the real live-mode candidate list (from the `llm_f_only` probe run) included `PLTR` (Palantir) — a company added to the S&P 500 in September 2024, after this project's stored 2020-2024 membership window ends (2024-04-30) — direct, real evidence that live mode is genuinely reading a fresh current membership snapshot rather than anything cached in `data/portfolio.duckdb`, which is exactly the kind of check this plan's Concrete Steps Step 4 asks for (though Step 4 itself, run against the default `llm_s_only` selection, remains for the "manually run" item below).
- Discovery (2026-09-04): implementing the editing loop exposed a real lifecycle bug in the live-mode design from the item above, caught before it shipped rather than after: `run_pipeline`'s live-mode branch opened `build_live_snapshot` and returned from inside that `with` block, so the temp snapshot file was already deleted (per its `finally: os.remove(...)`) by the time `run_pipeline` handed a result back to any caller. An interactive edit loop calling `load_returns_matrix`/`compute_weights`/`load_latest_prices`/`allocate_shares` again on an edited candidate list, using the same `db_path` the initial run used, would have pointed at a file that no longer existed for every live-mode session - a bug that a backtest-only call pattern could never surface, since backtest mode's `db_path` is a real, permanent file with no lifecycle to outlive. Fixed by extracting a new `open_pipeline_session` context manager that owns the snapshot's lifetime for an entire CLI session (initial run plus every edit) rather than one `run_pipeline` call; `run_pipeline` itself becomes a thin wrapper that opens one such session and returns after a single call, preserving its original one-shot contract and every existing caller (including item 19's own real end-to-end verification runs, re-confirmed still passing after this refactor).
- Discovery (2026-09-04): naively chaining `run_pipeline` 52 times for `run_full_backtest` would have been a real correctness bug, not just a wasted-cost one - `generate_rule`'s docstring already documents that it is intentionally non-deterministic across repeated calls for the *same* `year` (an accepted feature of plan 2's design, not something to "fix"), but nothing about that intentional non-determinism licenses calling it 12 separate times to derive "the rule for 2020" - README's Backtest Mode Stage 1 framing (`S_2020`, `S_2021`, a single named rule per year) and `plans/02_llm_s_agent.md`'s own framing ("one year's screening rule") both describe one rule generated once per year and then applied at every rebalance within it. This was caught by working out the consequence in advance (documented below in the Decision Log, not discovered via a failed run) rather than by observing an actual inconsistency in real output; the real 52-month run's transcript nonetheless independently confirms the fix works as intended - exactly 5 `Crew Execution Completed` events appear in the full transcript, one per distinct calendar year (2020-2024), each keyed to a distinct real causal-masking date (`2020-01-01` via the documented year=2020 fallback, then `2020-12-01`, `2021-12-01`, `2022-12-01`, `2023-12-01`), not 52.
