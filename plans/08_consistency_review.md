## Purpose / Big Picture

`README.md` describes what this project is supposed to do: build a factor dataset, run an LLM-S agent and an LLM-F agent, scan candidates, optimize portfolio weights, and coordinate all of that through an interactive flow, in both a historical "Backtest Mode" and a live "Live Mode." The seven plans under `plans/` (`01_dataset.md` through `07_external_candidate_screening.md`) are the ExecPlans that were actually written and executed to build this. Because README.md was expanded twice, on 2026-08-08 and 2026-08-09, after all seven plans had already been written and implemented, several parts of README.md now describe behavior that the plans and the shipped code under `src/` do not implement, and in a few places implement differently on purpose.

Before this plan existed, nobody had one place to see the full list of those gaps and mismatches. A contributor who wanted to trust README.md as ground truth, or who wanted to know which of the seven plans still needs work, had to re-read all seven plans (they total roughly 270KB of text) against the README line by line themselves. After this plan, that contributor can read this single file and see, for every paragraph of README.md's Configuration, Backtest Mode, and Live Mode sections, whether the plans/code already match it, and if not, exactly which file and line disagrees, why the disagreement exists, and which side (README.md's wording, or the plan/code) is recommended to change.

You can see this plan "working" by opening README.md side by side with the twelve numbered findings in the Decision Log below and confirming, for any one of them, that the quoted README passage and the quoted plan/code passage really do say what this document claims — every finding below cites an exact file and an approximate line number, and grep/git commands are given in Concrete Steps to reproduce each citation independently.

**Finding 4 — LLM-S's `year=2020` snapshot date does not match README's stated date.**
README's Backtest Mode Stage 1 (line 30) states: "LLM-S generate scan rules on 2019-12-31, and these rules are then applied to S&P 500 members at that time to get the candidates set $S_{2020}$." `src/agents/llm_s.py`'s `resolve_as_of_date` function (lines 25-33) computes "the most recent `factors` rebalance date in December of `year - 1`," but its own docstring states it "[f]alls back to the earliest available rebalance date if none exists before `year` started — the `year=2020` edge case, since this project's data starts 2020-01-01 with no prior-December snapshot — logging a warning because that year's rule is then not truly causally masked." `plans/02_llm_s_agent.md` (Progress, line 23; Decision Log, line 64) documents the same fallback and the same warning. In practice, `S_2020` is generated from a `2020-01-01` snapshot, not the `2019-12-31` snapshot README describes.
Decision: needs a user decision, but a low-stakes one. Either (a) update README to say the `S_2020` snapshot date is `2020-01-01` (the earliest available data point) with a footnote that this one year is not causally masked the way `S_2021`-`S_2024` are, or (b) backfill one December-2019 `factors` snapshot (if the underlying data source allows fetching data as of a date before the stated `fetch_start`/`rebalance_start` of `2020-01-01` in `settings.py`) so `2019-12-31` becomes real and matches README exactly. Recommendation: (a), since backfilling pre-window data conflicts with `settings.py`'s `rebalance_start = "2020-01-01"` and would require re-deriving whether SEC/price data even exists that far back for every S&P 500 constituent.
Rationale: this is already a known, logged, and accepted limitation in both the plan and the code's own docstring — it is not a silent bug, just a wording mismatch against README's idealized description.
Date/Author: 2026-08-10, consistency review.

**Finding 5 — LLM-F's implemented mechanism does not match README's Backtest Mode / Live Mode description of it.**
README's Backtest Mode Stage 1 (line 31) and Live Mode bullet 3 (line 49) both describe LLM-F's output as: "sentiment scores from exponentially-decreasing weighted sum of positive probability minus negative probability of [news articles]," with buy/sell/hold decided by thresholding that score at exactly `> 0.1` (buy) and `< -0.1` (sell). This is, verbatim, FinBERT's own mechanical scoring algorithm — and `plans/03_llm_f_agent.md` (Surprises & Discoveries, line 42) confirms this by quoting the reference paper's own description of FinBERT's algorithm in almost identical terms. But the actual `SentimentSignal` schema (`src/agents/llm_f_schema.py` line 19, and `plans/03_llm_f_agent.md` line 91) has fields `ticker`, `month`, `signal` (`buy`/`sell`/`hold`), `confidence` (0-1), and `rationale` — there is no numeric sentiment-score field anywhere, no exponential-decay computation, and no `±0.1` threshold. `src/agents/llm_f.py`'s module docstring (lines 1-13) explicitly acknowledges this: "this project's LLM-F instead has a general-purpose LLM read the actual headlines and make a holistic judgment call with a rationale, matching README.md's framing of LLM-F as replacing FinBERT's role rather than reimplementing FinBERT's specific mechanism" — but that framing is only true of README's intro bullet (line 8: "Implement LLM-F agent which replace the role of FinBERT"), not of README's own Backtest Mode and Live Mode paragraphs, which describe the specific mechanism as if LLM-F performs it.
Decision: needs a user decision — this is the single most consequential finding in this review, because README currently contradicts itself and the code has already picked a side. Two resolutions are possible: (a) rewrite README's Backtest Mode Stage 1 sentence and Live Mode bullet 3 to describe LLM-F's actual mechanism (an LLM reads headlines and produces a `buy`/`sell`/`hold` signal with a confidence and rationale, no numeric score or decay formula), which matches the shipped implementation and requires no code change; or (b) reimplement LLM-F to actually compute the exponentially-decreasing weighted positive-minus-negative probability score and threshold it at `±0.1`, which would require adding a numeric score output to `SentimentSignal`, a decay-weighting scheme over the LLM's per-headline judgments (or a separate probability-extraction step), and updating both `plans/03_llm_f_agent.md` and the Live Mode candidate-scanner integration in `plans/04_candidate_scanner.md`/`plans/06_interactive_flow.md` accordingly. Recommendation: (a), since (b) would mean discarding the deliberate, already-implemented, already-tested "holistic judgment" design in favor of re-mechanizing exactly the FinBERT-replacement behavior the project's stated goal (README line 8) is to move away from.
Rationale: README's own two descriptions of LLM-F cannot both be followed simultaneously; whichever the user does not pick needs to change, and that choice has downstream effects on `plans/04_candidate_scanner.md`'s `llm_f_only`/intersection/union branches and on Live Mode's `memory/F-summary.md` generation (finding 11), so it should not be decided implicitly by an implementer.
Date/Author: 2026-08-10, consistency review.

**Finding 6 — the optimizer's `expected_returns`/`cov_matrix` are unannualized, contradicting README's Stage 2 description.**
README's Backtest Mode Stage 2 (line 37) states: "The required parameters expected_returns and cov_matrix are calculated from 60 most recent monthly returns of each company in the portfolio set and then are annualized before given to EfficientFrontier." `src/optimizer/portfolio.py` lines 239-241 call `expected_returns.mean_historical_return(returns_matrix, returns_data=True, frequency=1)` and `risk_models.CovarianceShrinkage(cov_input, returns_data=True, frequency=1).ledoit_wolf()` — `frequency=1`, not `12`. `plans/05_optimizer_and_allocation.md`'s Context and Orientation section (line 98) and Decision Log (lines 69-71 area) explain this was a deliberate, documented choice: an earlier draft used `frequency=12` (which the plan confirms empirically produces an annualized figure, 12x the monthly one), and the plan's author changed it to `frequency=1` because `target_monthly_return` (see finding 7) is compared directly against `expected_returns` and needed matching units, calling the annualized version "a real unit mismatch."
Decision: needs a user decision — this is live in shipped code, not just plan prose, and reverting it has a specific consequence spelled out in the plan itself (see finding 7). Two resolutions: (a) update README's Stage 2 sentence to say expected_returns/cov_matrix are used "as monthly (unannualized) figures, with `target_monthly_return` expressed on the same monthly basis" — matching the shipped code and requiring no code change; or (b) change `src/optimizer/portfolio.py` to pass `frequency=12` (annualizing) and correspondingly change `target_monthly_return`'s default and all call sites to an annual target (see finding 7), matching README literally. Recommendation: (a), because switching to (b) reintroduces exactly the "unit mismatch" the plan's Decision Log already identified and fixed once — an annualized `expected_returns`/`cov_matrix` pair must be compared against an annual target return, and if that annual target is still `efficient_return`'s single scalar constraint, every other quantity flowing out of `EfficientFrontier` (Sharpe ratio inputs, `ef.portfolio_performance()`) also becomes annual, which then needs to be re-reconciled against the monthly rebalancing cadence (`t = 1..52`) that both README and every plan otherwise assume throughout Stage 2's return-series construction.
Rationale: this determines the units of every number Stage 2 produces (weights are unit-independent, but realized returns, Sharpe ratio, and the target-return constraint are not) — it is a genuine design decision with a paper trail already in the plan, not an oversight.
Date/Author: 2026-08-10, consistency review.

**Finding 7 — the MV objective's default target return is 1% monthly, not README's "12%."**
README's Backtest Mode Stage 2 (line 40) states: "By running the optimization for GMV, MV (12% target return), MSR, we will have all results to compare with." `src/optimizer/portfolio.py` line 224 defines `compute_weights(returns_matrix, objective, target_monthly_return: float = 0.01)` — a default of 1% *per month*, and the plan's Decision Log (line 54 area) justifies this as "matching the paper's own stated target," not README's 12% figure. Note 1% monthly compounds to roughly 12.7% annually, close to but not identical to README's 12%, and more importantly it is used as a monthly constraint against monthly `expected_returns` (finding 6), not derived from or equal to an annual 12% figure via any explicit conversion in the code.
Decision: needs a user decision, coupled to finding 6. If finding 6 resolves toward (a) (keep monthly, unannualized), then README's "12% target return" should become "a monthly target return, defaulting to 1%/month," matching the shipped default and the reference paper's own framing. If finding 6 resolves toward (b) (annualize), then `target_monthly_return`'s default and parameter name would need to change to an annual `target_return` at 12%. Recommendation: resolve alongside finding 6, in the same direction — (a).
Rationale: this is the same underlying units decision as finding 6, restated at the call-site level; resolving them independently would reintroduce the mismatch.
Date/Author: 2026-08-10, consistency review.

**Finding 8 — transaction cost and risk-free rate are entirely unimplemented.**
README's Backtest Mode Stage 2 (lines 38, 41) states that `pypfopt.objective_functions.transaction_cost()` should be used to convert gross returns into net returns $r_t$, and that "[b]oth transaction cost and risk-free rate which we need for the Stage 2 calculation are configurable constants and have default values as 10 basis point and 2%." `src/config/settings.py` (read in full — see Artifacts and Notes) has no `transaction_cost` or `risk_free_rate` field. `grep -rn "transaction_cost\|risk_free\|basis point" src/ plans/05_optimizer_and_allocation.md` returns no matches for any of these terms in either the shipped optimizer code or plan 05. `plans/06_interactive_flow.md`'s `run_full_backtest` (line 72) computes Sharpe ratio directly from raw `monthly_return` values with no transaction-cost deduction and no risk-free-rate subtraction (see finding 10).
Decision: needs a user decision, and unlike findings 6/7 this looks like a genuine gap rather than a considered alternative — no plan or Decision Log entry anywhere argues against implementing transaction cost or risk-free rate, they are simply absent. Recommendation: implement them as README specifies — add `transaction_cost_bps: float = 10.0` and `risk_free_rate: float = 0.02` fields to `src/config/settings.py`, wire `pypfopt.objective_functions.transaction_cost()` into the return-computation path described in `plans/06_interactive_flow.md`'s `run_full_backtest` (assuming $\hat{w}_{0,j} = 0$ for the first period as README specifies), and use `risk_free_rate` in the Sharpe ratio calculation (finding 10). This should be tracked as its own follow-up plan given its size (it touches both `plans/05_optimizer_and_allocation.md`'s `compute_weights`/allocation functions and `plans/06_interactive_flow.md`'s `run_full_backtest`).
Rationale: unlike findings 5-7, there is no existing design rationale anywhere in the plans for omitting this — it reads as unfinished work relative to README's Stage 2 spec, not a considered simplification.
Date/Author: 2026-08-10, consistency review.

**Finding 9 — no LLM-S-only default-selection mode exists in the interactive flow.**
README's Backtest Mode Stage 1 gained a new sentence in commit `4953940` (2026-08-09, the most recent of the three README-expanding commits): "LLM-F only selection and LLM-S + LLM-F selection are all expensive evaluation. LLM-S only selection is the default selection." `plans/06_interactive_flow.md`'s `run_pipeline` (line 63) unconditionally "runs `generate_rule`... then `screen`... runs `screen_month`... runs `scan_with_detail` on both signal sets" — every invocation computes both LLM-S and LLM-F and feeds both into the scanner's intersection/union branches (see `plans/04_candidate_scanner.md`'s `llm_s_only`/`llm_f_only`/`intersection`/`union` branches, which do exist and are correct per finding 12, but `run_pipeline` never selects the `llm_s_only` branch by default or exposes a way to skip the LLM-F call). `run_full_backtest` (line 72) chains `run_pipeline` across all 52 months the same unconditional way.
Decision: needs a user decision on how to expose the mode, but the direction is clear: implement it, since it is README's most recently and deliberately added sentence, added specifically to describe cost-saving behavior for backtest runs across 52 months × up to ~500 tickers. Recommendation: add a `selection: str = "llm_s_only"` parameter to `run_pipeline` and `run_full_backtest` (literal values `"llm_s_only"`, `"llm_f_only"`, `"llm_s_and_f"`), defaulting to `"llm_s_only"`, and skip the `screen_month`/LLM-F call entirely (not just ignore its result) when `selection == "llm_s_only"`, since README frames the other two modes as "expensive evaluation" implying the LLM-F call itself, not just its downstream use, should be avoidable.
Rationale: this is the freshest and most explicit piece of README text audited in this review, added one day before the review began, and plan 06 (last touched 2026-08-05, four days earlier) has had no opportunity to reflect it yet.
Date/Author: 2026-08-10, consistency review.

**Finding 10 — the backtest Sharpe ratio formula omits transaction cost and risk-free rate.**
README's Backtest Mode Stage 2 (line 39) states "[t]he sharpe ratio, mean, variance of $r_t$" (the *net*, transaction-cost-adjusted returns) "will give us Sharpe Ratio, Returns and Variance as the Table 1 of the paper," and the Sharpe ratio classically subtracts the risk-free rate from the return before dividing by the standard deviation, which is exactly why README calls out a risk-free-rate default (line 41). `plans/06_interactive_flow.md`'s `run_full_backtest` (line 72) instead computes "an annualized Sharpe ratio... (mean monthly return divided by monthly return standard deviation, multiplied by the square root of 12)" directly from gross `monthly_return` values — no transaction-cost deduction, no risk-free-rate subtraction.
Decision: needs a user decision — this is the same gap as finding 8, restated at the specific formula that is supposed to consume its output. Recommendation: resolve together with finding 8; once `transaction_cost` and `risk_free_rate` exist as settings, update `run_full_backtest`'s Sharpe calculation to `(mean(r_t) - risk_free_rate/12) / std(r_t) * sqrt(12)` using the net returns $r_t$ rather than gross `monthly_return`.
Rationale: implementing finding 8's constants without also fixing this formula would leave them defined but unused at the one place README says they matter most (matching the paper's Table 1).
Date/Author: 2026-08-10, consistency review.

**Finding 11 — Live Mode's entire persistent-memory architecture is unimplemented and uncovered by any plan.**
README's Live Mode section (lines 43-54), added by commit `b9f8d19` on 2026-08-08, describes a persistent-file architecture with specific staleness rules: `memory/rules.json` (stale after a full previous year), `memory/candidates.json` holding both $S$ and $S \cap F$ (stale after a season for $S$, after 30 days for $S \cap F$), `memory/S-summary.md` and `memory/F-summary.md` (each regenerated and the old file removed on refresh), `memory/analysis.md` (append-only, 30-day-old entries pruned), `memory/U-summary.md` (populated by moving entries out of `memory/analysis.md` when a user adds a candidate to $U$), `memory/long-term.md` (user-remembered risk-free/target-return overrides), and `output/GMV-{set}-portfolio-{date}.md`-style files for `{set}` in `S`, `SF`, `U`, `SU`, `SFU`. `grep -rn "memory/\|output/" src/ plans/` returns zero matches anywhere in the shipped code or any of the seven plans.
Decision: this is a scope gap, not a contradiction — no plan claims to implement Live Mode's persistence layer, so there is nothing to "fix" in the existing plans. Recommendation: track this as new work, e.g. a `plans/09_live_mode_memory.md`, rather than folding it into this review. That new plan would need to specify: the exact JSON/Markdown shapes of each `memory/*` file; where staleness timestamps are stored and compared (a `generated_at` field inside each file seems natural); how `plans/06_interactive_flow.md`'s flat `edit_candidates` list becomes three independently-tracked sets $S$, $S \cap F$, $U$ with union/intersection combinations; and how the existing `run_pipeline`/`run_full_backtest` functions relate to a new live-mode entry point that checks and refreshes these files before running.
Rationale: Live Mode is a substantial, mostly self-contained feature addition on top of Backtest Mode's existing pipeline; treating it as one more "inconsistency to patch" would understate the amount of new design work involved, so this review scopes it out as follow-up work instead of proposing a small fix.
Date/Author: 2026-08-10, consistency review.

## Context and Orientation

An "ExecPlan" is a design document, described in full in `/app/agentic_portfolio/PLANS.md` (checked into the repository root), that a coding agent or a human contributor can follow to deliver a working change to this repository without any other context. This repository already has seven of them, one per major implementation step named in README.md's introduction: `plans/01_dataset.md` (the DuckDB-backed factor dataset build), `plans/02_llm_s_agent.md` (the LLM-S rule-generation agent), `plans/03_llm_f_agent.md` (the LLM-F sentiment agent, meant to replace a model called FinBERT that the reference paper this project follows used), `plans/04_candidate_scanner.md` (combining LLM-S's and/or LLM-F's outputs into a candidate ticker list), `plans/05_optimizer_and_allocation.md` (turning a candidate list into portfolio weights and then into a whole-share allocation), `plans/06_interactive_flow.md` (the top-level pipeline and CLI that chains all of the above, in both a historical "Backtest Mode" replay and a "Live Mode" using current data), and `plans/07_external_candidate_screening.md` (letting a user screen tickers outside the S&P 500, including ETFs).

"Backtest Mode" and "Live Mode" are the two operating modes README.md (`/app/agentic_portfolio/README.md`, its own two section headers of the same names, lines 25 and 43) describes for this system. Backtest Mode replays the whole pipeline across a fixed historical window, 2020-01-01 through 2024-04-30, so its results can be compared against the reference paper's own reported numbers. Live Mode runs the same kind of pipeline against whatever is happening today, and — per README's Live Mode section — is meant to cache its intermediate results to disk under a `memory/` directory and write user-facing reports under an `output/` directory, refreshing each cached file only when it becomes stale by a rule specific to that file (a year, a season, or 30 days, depending on the file).

This review reads all seven plan files and README.md as they exist in the working tree at commit `4953940` (the tip of `master` as of 2026-08-10), and additionally inspects four source files directly to confirm findings that are live in shipped code rather than only described in plan prose: `src/config/settings.py`, `src/optimizer/portfolio.py`, `src/agents/llm_s.py`, and `src/agents/llm_f.py` (and its sibling schema file `src/agents/llm_f_schema.py`).
