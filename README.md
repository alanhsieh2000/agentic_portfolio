# Agentic Portfolio

This project aims to follow the idea proposed by "Designing Agentic AI-Based Screening for Portfolio Investment" (https://arxiv.org/abs/2603.23300v1). It provides an approach to evaluate portfolio selection automation. To use this approach, this project will need to:

- Build the dataset that includes 3 factors: log firm size (mve), book-to-market ratio (bm), and 12-month momentum
(mom12m) for all S&P 500 member companies during 2020-01-01 and 2024-04-30.
- Implement LLM-S agent.
- Implement LLM-F agent which replace the role of FinBERT.
- Implement the candidate scanner that uses the rules proposed by LLM-S and/or LLM-F agents.
- Build the optimization tool that provides GMV, MV, MSR weights for given and user input candidates.
- Implement the consolidation tool that converts weights into allocation in shares according to the market prices.
- Implement an interactive agent flow that coordinates the all agents of this system and modifies candidate set per user's request.

# Configuration

Runtime settings (DuckDB path, fetch/rebalance date windows, batch sizes, rate-limit pause seconds, HTTP timeouts, the book-equity reporting lag, the trailing dividend-yield window, and the LLM model name) are centralized in `src/config/settings.py`, a `pydantic-settings` `Settings` class with sensible defaults — see that file for the authoritative list of every configurable value and its default. Any field can be overridden via an environment variable of the same name (case-insensitive) or via a `.env` file at the repository root (gitignored, never commit one with real secrets).

Environment variables this project depends on:

- `SEC_UA` (required for the dataset build's SEC EDGAR fetches) — a descriptive User-Agent string (e.g. `"Your Name your.email@example.com"`); SEC returns HTTP 403 without one.
- `ANTHROPIC_API_KEY` / `ANTHROPIC_BASE_URL` (required for LLM-S/LLM-F's CrewAI Anthropic calls) — read directly by the `anthropic` SDK underneath `crewai`, not by this project's own code.
- `LLM_S_MODEL` (optional) — overrides the default Claude model LLM-S uses (`anthropic/claude-sonnet-4-5`).
- `RISK_FREE_RATE` (optional) — the annual risk-free rate every Sharpe ratio is measured against, as a decimal (default `0.02`). A per-currency rate remembered in `memory/rates.json` **outranks** this variable, deliberately: a per-currency entry is the more specific statement, and one global variable cannot express "0.5% for yen, 4.25% for dollars" at all. Every report names the source it actually used, so a run that ignores this variable says so.
- `DIVIDEND_LOOKBACK_MONTHS` (optional) — the trailing window a per-ticker dividend yield is computed over, in months (default `12`, the trailing-twelve-month convention). A ticker's yield is the per-share dividends with an ex-date in this window divided by its latest price.
- `DB_PATH` (optional) — overrides the default DuckDB file location (`data/portfolio.duckdb`).

# Backtest Mode

The backtest period is from 2020-01-01 to 2024-04-30. There are 2 stages:

- Stage 1
  - LLM-S generate scan rules on 2019-12-31, and these rules are then applied to S&P 500 members at that time to get the candidates set $S_{2020}$. Repeating the same process for the following years, that will give us $S_{year}$, where $year = 2020..2024$.
  - LLM-F generate sentiment scores from exponentially-decreasing weighted sum of positive probability minus negative probability of 2019 December news articles for each S&P 500 members on 2019-12-31, and these sentiment scores divide S&P 500 members into buy group for score > 0.1, sell group for score < -0.1, and hold group for others. Buy and sell groups together consist the candidates set $F_0$. Repeating the same process for the following months, that will give us $F_{t}$, where $t = 1..52$.
  - For LLM-S only selection, the portfolio set $P_{t} = S_{2020 + \lfloor (t-1) / 12 \rfloor}$, where $t = 1..52$.
  - For LLM-F only selection, the portfolio set $P_{t} = F_{t}$, where $t = 1..52$.
  - For LLM-S + LLM-F selection, the portfolio set $P_{t} = S_{2020 + \lfloor (t-1) / 12 \rfloor} \cap F_{t}$, where $t = 1..52$. If any intersection is empty, the respective portfolio set $P_{t} = S_{2020 + \lfloor (t-1) / 12 \rfloor} \cup F_{t}$.
  - LLM-F only selection and LLM-S + LLM-F selection are all expensive evaluation. LLM-S only selection is the default selection.
- Stage 2
  - EfficientFrontier of PyPortfolioOpt is used to optimize weights of the portfolio set $P_{t}$. That will give us weights $\hat{w}_{t,j}$, where $j = 1..\lvert P_t \rvert$, and $t = 1..52$. The required parameters expected_returns and cov_matrix are calculated from 60 most recent monthly returns of each company in the portfolio set and then are annualized before given to EfficientFrontier. In case that 60 months data is unavailable, at least 24 months data should be used. Companies with less than 24 monthly returns should be removed from the portfolio set.
  - The annualized expected_returns and weights $\hat{w}_{t,j}$ can give us the gross return of the portfolio at time t. By using pypfopt.objective_functions.transaction_cost(), we may take the transaction cost into consideration just like what the paper did. We can assume $\hat{w}_{0,j} = 0$ for all $j$. That will give us the net returns $r_t$, where $t = 1..52$.
  - The sharpe ratio, mean, variance of $r_t$ will give us Sharpe Ratio, Returns and Variance as the Table 1 of the paper.
  - By running the optimization for GMV, MV (12% target return), MSR, we will have all results to compare with.
  - Both transaction cost and risk-free rate which we need for the Stage 2 calculation are configurable constants and have default values as 10 basis point and 2%.

# Live Mode

After we use the Backtest Mode to find effective and efficient values for hyper-paraments and see a promising result, we will be ready to use the Live Mode.

- LLM-S generate scan rules using currently available fundamental data of S&P 500 members and stores them in memory/rules.json, if the file is missing or rules in the file are out of date. The system decides whether LLM-S is needed or not automatically and shows the progress. When the timestamp of the latest rules is in the previous year or even earlier, they are out of date.
- These LLM-S rules are applied to the current S&P 500 members to generate the candidate set $S$. $S$ should be stored in memory/candidates.json. If the file is missing or $S$ in the file is out of date, the system refreshes them automatically and shows the progress. When the timestamp of the latest $S$ is in the previous season or even earlier, the are out of date. Seasons are defined as 1/1 - 3/31, 4/1 - 6/30, 7/1 - 9/30, 10/1 - 12/31. The system should make a summary for each candidate in $S$ and store this information in memory/S-summary.md. The old memory/S-summary.md will be removed.
- LLM-F generate sentiment scores from exponentially-decreasing weighted sum of positive probability minus negative probability of the most recent 30 days for each candidate in $S$ and stores the candidate set $S \cap F$ in memory/candidates.json. If the file is missing or $S \cap F$ in the file is out of date, the system refreshes them automatically and shows the progress. When the timestamp of the latest $S \cap F$ is earlier than 30 days ago, the are out of date. The system should make a summary for each candidate in $S \cap F$ and store this information in memory/F-summary.md. The old memory/F-summary.md will be removed.
- Users can ask the system to analyze candidates, including ETF. The system should use the current LLM-S rules, look up the most recent 30-day news, use LLM-F to generate sentiment scores, and make a summary for candidates. This information should be stored in memory/analysis.md. New analyzed summaries will be appended to the end, and summaries with timestamp older than 30 days will be removed from the file.
- Users can ask the system to add candidates to the candidate set $U$. $U$ should be stored in memory/candidates.json. For added candidates, the system will move summaries associate with them from memory/analysis.md to memory/U-summary.md.
- Users can ask the system to remove candidates from any candidate set, including $S$, $S \cap F$, and $U$. The system should also update memory/S-, F-, U-summary.md accordingly.
- Users can ask the system to calculate weights for GMV, MSR, MV, using $S$, $S \cap F$, $U$, $S \cup U$, $(S \cap F) \cup U$. The system will report summaries and store them as output/GMV-, MSR-, MV-{set}-portfolio-{date}.md, where {set} is 'S', 'SF', 'U', 'SU', or 'SFU'.
- The risk-free rate every Sharpe ratio is measured against is remembered **per currency** in `memory/rates.json`, because a risk-free rate is a property of a currency — the riskless asset is a short-dated government bill in that currency — and this project's portfolios each hold exactly one currency, so a single global value cannot be right for a dollar and a yen portfolio at once. Measuring a yen portfolio against the 2% dollar default subtracted the wrong number, which is what this file fixes. `--risk-free-rate` on either `uv run portfolio` or `uv run portfolio-holdings` overrides the rate for that run and is remembered for the run's currency; left out, the rate is whatever that currency remembered, else the configured `RISK_FREE_RATE`, else 2%. Every report prints which of those sources it used (`Risk-free rate used: 0.0050 (remembered for JPY)`), because a bare number is precisely what the bug looked like. One resolved rate reaches the pool's figures, the benchmark's and your own holdings' alike, so the three lines a report prints one under another stay on one scale. Only an explicit choice is ever written to the file, never a default, so improving the default later still reaches every currency that never named one; rates are decimals (4.25% is `0.0425`), negative rates are accepted because policy rates have been negative, and a value of 1 or more is refused as a mistyped percentage rather than remembered and left to break every later `MSR` run. There is deliberately no built-in table of per-currency rates, unlike the benchmark's `SPY` default for USD: an index stands for a market for decades, but a policy rate moves several times a year, so a compiled-in table would rot. Backtest Mode is untouched and still uses the configured rate, so its published figures cannot move. Remembering a **target return** rate is not implemented; `--target-return` remains per-run, and `memory/long-term.md` remains unbuilt.
- Each candidate pool is measured against a benchmark, and the report prints that benchmark's annual return, annual volatility and Sharpe ratio over exactly the same window of monthly returns the portfolio's own figures came from, using exactly the same estimators, so the two lines can be read side by side. `SPY` is assumed for a USD pool. No other currency is assumed for: there is no single obvious index for a yen or sterling pool, so rather than quietly measure a portfolio against something nobody chose, the system asks once and remembers the answer in `memory/candidates.json` beside that pool's tickers. `--benchmark TICKER` overrides it for a run (and, for `--selection user_provided`, is remembered), `[b]enchmark` in the interactive loop changes it at any time, and `--benchmark none` leaves the comparison out. A benchmark must trade in the pool's own currency and is refused by name otherwise, because comparing a yen portfolio's yen return against `SPY`'s dollar return would present the year's exchange-rate move as though it were performance. The benchmark is never a holding: it receives no weight and never joins the candidate pool. Its price history is fetched into a throwaway database of its own, never into the session's, so the shared `data/portfolio.duckdb` cache is only ever read and the benchmark can never influence the window the portfolio itself is measured over; `--no-benchmark-fetch` restricts it to whatever the session's database already holds, keeping a backtest-window run entirely offline at the cost of reporting the benchmark as unavailable. A benchmark that cannot be resolved, has too little history, or trades in the wrong currency is reported as a one-line `n/a` with the reason and never interrupts the run.
- Beside the candidate pools it considers, the system remembers the portfolio the user **actually holds**: tickers and the number of shares of each, stored per currency in `memory/portfolio.json` and maintained with `uv run portfolio-holdings`. `set SPY 1000 T 500` records or updates holdings, `set T 0` retires one, `remove T` drops it, and a bare `uv run portfolio-holdings` reports every saved portfolio. Share counts may be fractional. One portfolio per currency, for the same reason a candidate pool is single-currency: prices in two different units cannot be weighed against one total, and no conversion is implemented. Which portfolio an edit lands in therefore follows from the ticker itself - `set SPY 1000` edits the USD portfolio and `set 1321.T 50` edits (or creates) the JPY one - so naming two currencies in one `set` refuses the second by name rather than editing two portfolios at once; `--currency` targets one explicitly. Every added ticker is validated against Yahoo Finance first, so a typo is reported rather than silently stored. Recording a holding never writes to `data/portfolio.duckdb`: the prices and returns needed to measure it are fetched into a throwaway database of their own, exactly as a benchmark's history is, so printing a report can never add rows to the shared cache or move the window a candidate pool is measured over.
- The holdings' prices and monthly returns are cached in `data/holdings.duckdb`, so a repeated report costs no network. A ticker is refreshed when the cache does not hold its latest month's return — which means once a calendar month — and `--refresh-holdings` forces it sooner. That policy keeps the 60-month figures always current, but the *prices* behind `Total value` and the weights change daily, so a total read late in the month can be weeks old; the report therefore states the date it priced the holdings at (`Total value: $850,722.00 USD (priced 2026-09-04)`), read off the price rows actually used rather than off a refresh timestamp. Only the tickers a report asks about are refreshed, so the file never becomes a list of everything ever tried that must all be refetched together. It is deliberately a separate file from `data/portfolio.duckdb`: that one holds the S&P 500 universe candidate pools are measured against, and `--no-holdings-fetch` — which now reads the cache too, since a local file is not a network call — must never see holdings rows land there, because the returns window is derived from the whole table. `--holdings-cache-path` points it elsewhere.
- `uv run portfolio-holdings whatif` answers "what would happen if I changed something?" without changing anything. It prints the saved portfolio's figures, then opens a loop — `[s]et shares / [r]emove / [u]ndo all / [f]inish` — reporting the hypothetical portfolio and the signed change in annual return, volatility and Sharpe after each edit. It is the one interactive subcommand and the one that saves nothing at all: not the positions, and not a `--risk-free-rate`, which every other subcommand remembers (so "what if the riskless return were 5%?" is askable without consequences). Every variant is measured against one throwaway database opened once, which means they all share a single returns window — a Sharpe difference across two different windows would be partly a difference of months rather than of holdings, so the report withholds the delta and says so if that ever fails to hold. A ticker you do not already own is validated as `set` validates it, so a cross-currency one is refused by name rather than quietly dropped from the figures; under `--no-holdings-fetch` it is refused outright, since adding it would mean writing to the shared price cache. On finishing, the exact `uv run portfolio-holdings set ...` command that would apply the experiment is printed, so a good result costs no retyping while the never-save guarantee stays absolute. `[w]indow` varies the other thing that moves the figures: the length of the returns window, anywhere from 24 to 60 months. That matters because the choice can dominate the answer — `PFF`, which fell hard in the earliest months of the 60-month window and has been stable since, reports a Sharpe of −0.28 over 60 months and +0.21 over 36 — so the window is named on the same line as the figures it produced (`36 month(s) of monthly returns, 36 requested`), the request shown beside the count actually used so a chosen window is never mistaken for all the data there was. Changing it re-measures the saved portfolio too, keeping both sides of the comparison on one window. Everything outside the loop still measures over the fixed 60.
- Every `uv run portfolio-holdings ...` command, and every `uv run portfolio ...` run, ends by printing that portfolio's annual return, annual volatility and Sharpe ratio for the run's own currency, beneath the optimizer's own figures and the benchmark's - and, above them, each individual holding's annualized expected return and volatility, in the same `Expected return / volatility (annualized)` section and the same position an optimized pool's report has always used, so the two blocks read against each other line for line. Share counts become weights through each holding's latest market price (`shares × price` as a fraction of the whole), because a portfolio's risk depends on how its money is distributed rather than on how many pieces it is divided into. The three figures use the same estimators and the same risk-free rate as the pool's and the benchmark's — one rate, resolved once per run from the currency's own remembered value — so all three lines read on one scale - a portfolio holding only `SPY` reports exactly the numbers the `Benchmark SPY` line above it does. The returns window the figures came from is always printed, since the same holdings measured over different months are a different number. A holding with under 24 months of usable monthly returns, or with no price, is excluded from the figures and named with its share of total value rather than blocking the report - withholding a correct answer about 98% of a portfolio over a recently-listed 2% would be less useful, not more careful. `Total value` therefore counts every holding that can be priced while the weights cover only the measured ones; both denominators are honest ones and the gap between them is printed. `--no-holdings` leaves the block out of a pipeline run entirely, and `--no-holdings-fetch` (also spelled `--no-fetch` on `portfolio-holdings`, and the counterpart of `--no-benchmark-fetch`) restricts it to what the session's database already holds, keeping a backtest-window run offline at the cost of reporting the holdings as unmeasurable.
- Candidates listed on non-U.S. exchanges can be added using Yahoo Finance's suffix notation, for example `7203.T` for Tokyo or `BARC.L` for London. Each portfolio must use a single currency: the first ticker added establishes it, and a ticker priced in a different currency is refused by name rather than silently mixed in, because prices in two different units cannot be allocated against one budget. So a yen portfolio and a dollar portfolio are built as two separate runs, with `--value` interpreted in the portfolio's own currency (shown as the `Portfolio currency` line in the output). Exchanges that quote in a minor unit are normalized to the major one, so London's pence become pounds. All of these pools are kept together in memory/candidates.json, one per currency, and when more than one is saved the system lists them and asks which to resume, or lets you start a new one in another currency. `--currency JPY` answers that question from the command line instead, so a run can be scripted rather than waiting at a prompt; a currency with no saved pool starts a new one with that currency settled up front, which means a ticker in any other currency is refused by name instead of silently establishing a different pool. It applies only to `--selection user_provided` and is refused for the others, which screen the S&P 500 and are USD by construction. A candidates.json written before per-currency pools existed is read as the USD pool automatically; `uv run portfolio-migrate-candidates` converts it in place without a network call, keeping its original timestamp that an ordinary save would replace. Converting between currencies is not implemented; that would be required only for a single portfolio holding several currencies at once.

- A portfolio can be required to **pay** a minimum amount of dividend income, which no objective on its own expresses: GMV minimizes variance and MSR maximizes Sharpe, and either may return a pool of near-zero-yield growth names. `--min-annual-dividend 3000` refuses any portfolio expected to pay less than 3,000 of the portfolio's own currency over the coming year, and `--min-dividend-yield 0.03` states the same single constraint as a decimal yield instead — the two are two spellings of one thing (the cash amount is divided by `--value`) and naming both at once is refused rather than reconciled, since reconciling would mean discarding a number you typed. It applies to GMV, MV and MSR alike, as one linear constraint on the weights through PyPortfolioOpt's `add_constraint`. Each ticker's estimate is its **trailing twelve-month** yield — the per-share dividends actually paid in the last year over the latest price, fetched from Yahoo Finance into a `dividends` table by `uv run portfolio-build-dividends` and, for a ticker you type yourself, on the same pass that already fetches its prices. It is a record of what was paid, not a promise of what will be, and the report says so. Because weights are long-only and sum to 1, the best yield any portfolio of a given pool can reach is exactly its highest-yielding member's, so an impossible floor is refused up front naming that ticker and that ceiling (`the highest-yielding candidate is T at 0.0397`) rather than reported as a solver failure. Worth knowing: expected returns in this project come from `adj_close` and so are **total** returns that already include dividends, which means a dividend floor adds no new return — it shifts the composition of one the optimizer already saw from price appreciation toward cash, and the expected total return usually falls when the floor binds, because a floor can only shrink the set of portfolios available. Under `MV` a binding floor can therefore put `--target-return` out of reach, and the error says which two numbers collided and what the attainable return now is. `[d]ividend` in the interactive loop retunes the floor without restarting (a bare number of 1 or more reads as cash, below 1 as a yield, `3%` as a yield, `none` clears it, and the reading is echoed back), and an unreachable value reverts the edit instead of ending the session. Every report — the optimized pool's and your own holdings' — prints the yield and the annual income beside the expected return, always with the denominator it was computed over: a ticker whose dividend history is genuinely absent is named as such and left out rather than counted as a zero payer, because a missing yield is not a zero yield. Your saved holdings' dividend figures deliberately cover more holdings than their return figures do, since a trailing dividend needs no return history at all, and `whatif` reports the signed change in yield and income after each edit — unchanged by `[w]indow`, which is itself worth seeing, since it says the window cannot flatter the income. The report also states what the whole-share allocation itself would pay, which differs from the portfolio yield above it only by whole-share rounding — a fraction of a percent, since whole shares plus leftover cash cannot reproduce continuous weights exactly. Per-share dividend amounts come from Yahoo Finance on each ticker's **current** share basis, which means a payment made before a stock split is reported divided down by it — SoftBank Group (`9984.T`) declared ¥22 for its 2025-09-29 ex-date, split 4:1 on 2025-12-29, and that payment is therefore stored and summed as ¥5.50. That is correct (a holder of 1,000 shares today held 250 then, and really did receive ¥5,500 each time), but it is not the figure any announcement quotes, so whenever a split falls inside the trailing window the report says so and reconciles the two — naming the split, its date, and both amounts, all derived from the stored data rather than written down anywhere. A split also silently invalidates a **share count**: `memory/portfolio.json` holds raw numbers, so a holding recorded before a split is no longer the number of shares you own, and every figure derived from it — total value, weights, dividends — would be understated by the split factor while staying perfectly self-consistent. Every holdings report therefore checks each portfolio's own `updated_at` against the splits since, and warns above the figures it affects, naming the split and printing the exact `uv run portfolio-holdings set ...` command that would fix it. It never rewrites the file: a split is precisely the sort of event people also trade around, so only you know the true position. The check is per currency and uses the last edit to that portfolio, so it can miss a stale count but can never invent one — a warning telling you to quadruple a holding that was already right would be the worse failure. Backtest Mode is untouched and cannot acquire a floor at all: `compute_weights`, the function it calls, has no parameter to pass one through, so its published figures cannot move.
